# Контракт агента PolymarketLab

## Проект

PolymarketLab регистрирует рынки Polymarket, собирает исходные сообщения WebSocket в PostgreSQL и строит нормализованные проекции. Серверная часть является источником истины; клиентская часть управляет ею через HTTP API.

Стек технологий: .NET 10, ASP.NET Core, MediatR, FluentValidation, EF Core, PostgreSQL, React 19, TypeScript, Vite, TanStack Query, xUnit и Vitest.

## Структура репозитория

* `PolymarketLab.Api` — единственный исполняемый узел приложения.
* `PolymarketLab.Markets.*` — регистрация и чтение рынков.
* `PolymarketLab.DataCollection.*` — выполнение сборщика, приём исходных данных и построение проекций.
* `PolymarketLab.Framework`, `PolymarketLab.SharedKernel` — общие примитивы HTTP и предметной области.
* `PolymarketLab.Web` — панель управления на React; для неё также действует `PolymarketLab.Web/AGENTS.md`.
* `docs` — контракты и сведения о проекте.
* `observability` — Prometheus, Grafana, Loki и Alloy.

Архитектурные инварианты и ссылки на документы отдельных областей находятся в `docs/agent-context.md`. Перед изменением соответствующего модуля прочитай этот документ и ближайший `AGENTS.md`.

## Команды

Первоначальная настройка из корня репозитория:

```powershell
dotnet restore .\PolymarketLab.slnx
npm ci --prefix .\PolymarketLab.Web
.\.harness\setup.ps1
```

Локальный запуск:

```powershell
docker compose up -d postgres
dotnet run --project .\PolymarketLab.Api\PolymarketLab.Api.csproj --launch-profile http
npm --prefix .\PolymarketLab.Web run dev
```

Проверки:

```powershell
dotnet test .\PolymarketLab.slnx
dotnet build .\PolymarketLab.slnx
npm --prefix .\PolymarketLab.Web run test
npm --prefix .\PolymarketLab.Web run typecheck
npm --prefix .\PolymarketLab.Web run build
git diff --check
```

Сначала запускай наиболее узкий подходящий тест, затем расширяй объём проверки. Полный набор интеграционных тестов .NET требует доступного Docker daemon. Отдельная команда для статического анализа исходного кода в репозитории не настроена.

## Рабочие правила

* Отвечай по-русски, если пользователь не попросил другой язык.
* Все объяснения, планы, вопросы, промежуточные отчёты, результаты проверки кода и итоговые ответы должны быть на русском языке.
* В общении не смешивай русский и английский языки: английский используй только для исходного кода, технических идентификаторов, команд и дословных сообщений инструментов.
* Исходный код, имена классов, методов, переменных, файлов, каталогов, команды, ключи конфигурации, названия API и другие технические идентификаторы оставляй на языке проекта.
* Не переводи сообщения об ошибках, журналы и цитаты из внешней документации. При необходимости объясняй их смысл на русском языке.
* Комментарии в коде пиши в соответствии с уже существующими соглашениями проекта. Не переводи существующие комментарии без явной просьбы пользователя.
* Не отвечай на английском языке, если пользователь явно не попросил об этом.
* Когда пользователь просит изучить, взять или спланировать задачу до реализации, обязательно вызови навык `analyzing-tasks`. Сначала объясни назначение задачи простыми словами и приведи конкретные примеры успешного сценария, сценария ожидания и ошибочного сценария. Для числовых значений явно указывай смысл и единицы измерения, например цену `0.01`, вероятность `1%` или конечное расчётное значение `1.00`.
* Сохраняй существующую архитектуру и делай минимальные изменения в рамках задачи.
* Фактический код серверной части, контроллеров и DTO имеет приоритет над документацией API.
* Для моделей и интерфейсов C# добавляй содержательные XML-комментарии на русском языке к типам и их членам, включая семантику `null`.
* Ожидаемые ошибки не превращай в исключения и не скрывай исходный код или сообщение интеграционной ошибки.
* Не изменяй и не удаляй чужие незавершённые изменения.
* Не добавляй учётные данные, токены, строки подключения или полные исходные данные сообщений в код, документы, команды и отчёты.

Можно самостоятельно менять код, тесты и документацию в пределах поставленной задачи и запускать локальные проверки. Сначала спроси разрешение на:

* изменение публичного HTTP-контракта или границ модулей;
* создание или применение миграции EF;
* обновление версий зависимостей;
* добавление MCP, перехватчиков, непрерывной интеграции, разрешений среды выполнения или учётных данных;
* разрушительные операции с Docker, базой данных или Git;
* создание коммита, отправку изменений, перебазирование, создание ветки или запроса на слияние.

Не изменяй вручную снимки состояния миграций, сгенерированные артефакты, файлы в `bin`, `obj`, `node_modules`, `dist` и чувствительные к побайтовому содержимому тестовые данные в `PolymarketLab.DataCollection.Infrastructure.Tests/Fixtures/Polymarket`.

## Критерии завершения

* Поведение покрыто тестом на подходящем уровне либо явно объяснено, почему тест не требуется.
* Выполнены относящиеся к задаче команды тестирования, проверки типов и сборки; ограничения окружения указаны.
* `git diff --check` проходит, а итоговый набор изменений не содержит несвязанных правок и секретных данных.
* Документация и контракты API обновлены, если поведение изменилось.
* Итоговый отчёт содержит причины изменений, перечень изменённых файлов и результаты проверок.

## Проектные инструкции

Канонические локальные инструкции проекта находятся в `.harness/skills`, а их происхождение закреплено в `.harness/harness.lock`. OpenCode обнаруживает их через локальное соединение `.agents/skills`, создаваемое явной командой `.\.harness\setup.ps1`. После клонирования или перемещения репозитория выполни настройку и `.\.harness\health.ps1`.

Контракт проекта всегда имеет приоритет над процедурными инструкциями. Действуют следующие уточнения:

* `superpowers:test-driven-development` соответствует локальной инструкции `tdd`, а `superpowers:verification-before-completion` — критериям завершения и командам проекта.
* Отсутствующие `using-git-worktrees`, `subagent-driven-development`, `executing-plans` и другие возможности не устанавливай автоматически; используй доступные возможности среды выполнения и контракт репозитория.
* `brainstorming` используй для крупных или неоднозначных возможностей, а не как обязательную процедуру перед ограниченной по объёму задачей; `writing-plans` — для работы с несколькими модулями и несколькими существенными этапами либо по прямому запросу.
* `brainstorming`, `domain-modeling`, `writing-plans` и `research` не создают постоянные документы, `CONTEXT`, ADR или планы и не создают коммиты без явного запроса; для знаний о предметной области используй `docs/agent-context.md` и текущую документацию предметной области.
* `codebase-design` не переопределяет установленную терминологию DDD, .NET и React или границы модулей.
* `code-review` не требует системы учёта задач: спецификацией может быть запрос пользователя, текущий набор изменений или существующий документ проекта.
* `systematic-debugging` не показывает секретные данные или полное содержимое исходных сообщений, использует PowerShell и команды тестирования проекта; вспомогательные средства POSIX необязательны.
* `writing-skills` не разрешает удалять изменения пользователя, создавать коммиты, отправлять изменения или создавать внешние артефакты.
